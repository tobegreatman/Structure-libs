# A股市场主线分析 · 提示词模板 + HTML 报告页

一套可直接投产的「提示词 → 结构化 JSON → 报告页」闭环。把提示词交给任意具备取数能力的模型或 Agent，拿回严格 JSON，导入本页即渲染成完整分析报告。

> 当前版本：提示词 **v1.6** · 契约 `1.0.0` · 测试 **54** 条 · 页面体检覆盖 **12 类**可复算规则
> v1.5 的主题是**判据可复算**：五个阶段的每条判据都有对应字段，页面拿这些字段把结论重算一遍，算不出来就标出来，不替你圆。
> v1.6 的主题是**口径不打架**：同一份报告只允许一套面板/粒度，闸门必须全样本穷举，阈值按原始精度比较，阶段无法赋值者不进榜，并把「闸门矩阵」写进数据质量说明。

├── schema/ashare-mainline.schema.json # 输出契约（JSON Schema draft-07）

页面**不发起任何外部请求**：Vue 与 Inter 都在本地（`vendor/`），断网、file:// 直开都能拿到完整字形，控制台不会有 `fonts.gstatic.com` 的加载失败。

## 快速开始

1. 双击 `index.html` 打开（无需服务器，file:// 直开即可）。
2. 点右上角「提示词模板」→「完整版（API/Agent）」，点「复制完整版」。适用于 API / Agent / 有文件写入能力的运行环境。
3. 把提示词里的 `{{AS_OF}}` 换成目标交易日，连同数据源说明一起发给模型。
4. 得到输出后点「导入」→ **整段粘贴即可**（markdown 代码块、前后的「以下是分析结果」都不用删）→ 解析并渲染。

页面默认展示的是 **示例数据（合成，非真实行情）**，右上角有「示例数据」标记，页脚也做了声明。导入真实数据后标记会随之变化。

## v1.6 补了什么

v1.6 不改契约、不改阈值，只把实盘复算时暴露的「同一份报告里三套数打架」问题写成硬规则：

- **单一真源**：`metrics` / `persistence` 必须来自同一面板、同一板块粒度、同一横截面；「白酒+休闲」这类集群口径只能在 `rotation` 定性使用，且要注明差异。
- **闸门可穷举**：写「唯一 / 只有 / 仅」前必须对全样本算完 P1/P2/P3；P2 未计算的板块不能算作「未通过」。P2 的新高定义固定为「收盘价高于前 20 个交易日（不含当日）最高收盘价」，成分股覆盖率 <80% 时记「无法判定」。
- **边界值不四舍五入**：`turnover_share_chg_5` 按 4 位小数比较；距阈值 <5% 的指标必须在 `notes` 标「边界值」并给出另一口径结果。
- **阶段不可判定不进榜**：通过 ≥2 条闸门但 §4 判据不足 2 项的板块，只能进 `rotation.emerging`；`data_quality.notes` 必须写一条 `板块 | P1 | P2 | P3 | 闸门命中 | 阶段命中 | stage` 的闸门矩阵。
- **口径公式写死**：`rs = (1+板块收益)/(1+基准收益)`；`fundflow` 用 `N 日净额 ÷ 同期成交额`；`turnover_share` 分母优先全市场成交额；`coverage` 必须给可复算算式。
- **其他防错**：`rotation.emerging.score` 必须六因子实算；`excluded` 只写面板真实缺行；同日修订版必须在 changelog 说明上一版错在哪；没有两融数据就不写「杠杆退潮」。

## 为什么是这套时间粒度

单一窗口必然失真：太短会被单日脉冲欺骗，太长会把走完的行情当成进行中的主线，再长则数据不可得。

| 窗口 | 交易日 | 角色 | 判断权重 | 理由 |
|---|---|---|---|---|
| T 日 | 1 | 仅确认，不单独判定 | 0% | 单日涨停潮可能来自消息脉冲、指数调仓、期指交割 |
| 短窗 | 5 | 脉冲过滤 | 20% | ≈1 周，足够让消息驱动资金露出真伪 |
| **主窗** | **20** | **主判定** | **45%** | A 股题材情绪周期通常 15~40 个交易日，20 日≈一个完整发酵周期 |
| 中窗 | 60 | 中期定性 | 20% | ≈1 季度，跨一次财报或政策窗口 |
| 长窗 | 250 | 历史分位（P3 闸门 + 惩罚） | 15% | ≈1 年，拥挤度/估值的统计基础 |

合计 100%。**这是「判断权重」，不是打分权重**——它说明为什么以 20 日为主窗，不进入 `score` 的算术；`score` 只由六因子的 `normalized × weight` 决定。

配套的**反脉冲三原则**（持续性 / 广度 / 量能）要求候选板块至少通过 2 条才能作为常规主线；仅 1 条时 `stage_confidence ≤ 0.5` 且不得标 `acceleration`，0 条不进榜。通过 ≥2 条但 §4 无法赋值 `stage` 的，也只能进 `rotation.emerging`。这是本方案与「看今天哪个板块涨得最多」的根本区别。唯一例外是 `fade`（退潮）：退潮中的板块份额必然在缩，P3 天然过不了，所以已在榜的老主线可以**保留一期**——但必须同时标 `stage=fade`、`stage_confidence ≤ 0.6`、并进 `rotation.outflow`，下一期强制移出。

## 数据源

P0 全部免费公开、稳定可得：

- 交易所官网：日线、成交额
- 东方财富两融市场汇总 `RPTA_RZRQ_LSHJ`：融资/融券/两融余额、融资净买入、占流通市值比（**相对报告日滞后 1 个交易日**；不要用沪深分市接口相加，两市披露不同步会让合计数出现「半天更新」）
- 东方财富板块行情：板块指数、成交额、换手、成分股涨跌
- 东方财富涨停板行情：涨停家数、连板数、封板率（收盘后）
- 东方财富资金流：主力净额（**算法测算值**，权重上限 10%）
- 中证指数官网：指数点位与 PE/PB 历史分位
- 新浪财经全 A 快照（`node=hs_a`）：全市场涨跌家数、涨跌比、成交额核对（`push2` 不可用时的主力通道）

**已知的坑（模板里已写死约束）**：

- 沪深港通自 2024-08 起不再披露日度净买入与实时额度余额 → 禁止把「北向净流入」当日度因子，改用陆股通持股变动（周度）或直接省略。
- 资金流是按单笔金额分档推断的测算值，不等于真实席位行为，必须标注口径。
- 取不到的字段写 `null` 并在 `data_quality.missing` 说明，禁止 0 填充、禁止编造。
- 板块横截面必须用 `RPT_INDUSTRY_FUNDFLOW` 当日有数据的**全部**板块（2026-10-30 为 128 个）。按代码前缀或名称后缀筛子集会让前 10 名门槛失真：128 个里前 10 约 7.8%，86 个里约 11.6%，同一板块的 P1 天数能相差一倍（白酒 6/20 vs 11/20）。
- P1 的「进前 10」按**滚动 20 日累计涨幅**的横截面排名，不是当日涨跌幅。当日排名波动过大，按当日算会出现「单日 −2.33%、排全样本末位却连续 11 天进前 10」的矛盾。
- `push2.eastmoney.com` / `push2delay` / `82.push2` 的 `clist` 全市场快照在部分网络下**连接层被 RST**（HTTP 000），重试无效；全市场广度改走新浪 `Market_Center.getHQNodeData`（见第 8 条）。
- `push2his.eastmoney.com/…/kline/get` 已被应用层封禁（直连 RST，`RPT_BOARD_DAILY` 也不存在），板块日线成交额只能由资金流反推；`web.ifzq.gtimg.cn` 的日 K 有 WAF，**并发超过 3 rps 会返回 501 风控页**。

## 取数流水线

`pipeline/` 把「取数 → 闸门 → 报告组装」脚本化，替代逐次手写请求脚本。上一轮手工取数用了 36 分钟（其中 14.7 分钟是返工）；现在**全量真取** 156 次请求铺开 **45.8 秒**（并发 4 / 实测 3.40 rps / 失败 0 / 封禁 0），K 线库冷启动约 90 秒，之后走缓存。

注意这两个数不是同一个东西：早期版本用 12 并发 + 10 rps，面板 129 次请求 32 秒冲完，看着快，但节奏由 host 队列决定、全局无上限——WAF 501 与连接层 RST 就是这么来的。现在牺牲十几秒把请求摊开，换来的是「跑多少轮都不触发风控」。策略见下文第 7 条。

```
pipeline/
├── http.py        # 全局平滑限速 + host 限速 + 速率预算 + 自适应降速 + 重试 + 熔断 + journal
├── templates/fetch_policy.json  # 取数节奏的唯一真源（并发/rps/铺开时长/host 上限）
├── contract.py    # 接口契约前置校验（4 个源各 1 个样本，0.6 秒出结论）
├── panel.py       # 板块面板：涨跌幅 + 资金流 + 反推成交额 + 滚动收益排名
├── quotes.py      # 腾讯批量报价（60 只/批，232 只 4 次请求 0.8 秒）
├── breadth.py     # 全市场涨跌家数：新浪全 A 快照 56 页，push2 被 RST 时的备用通道
├── margin.py      # 两融余额：单请求取满 260 日，按 lag_trading_days 分级降级，不因滞后一刀切 null
├── kline.py       # 本地 K 线库（sqlite，复权序列 c + 原始价 r）+ 增量更新 + P2 广度
├── repair_kline.py# K 线库体检 / 补洞（--check 只报告，--rebuild 换口径重建）
├── report.py      # 报告模板化：静态块注入 + 一致性自检
├── templates/static.json  # 每期不变的块（weights/stage_rules/glossary/…）
├── run.py         # 编排 + 逐阶段计时
├── day.py         # 交易日自动推导（行情日历 + 磁盘缓存 + 本地库降级），--as-of 缺省即 auto
├── daily.py       # 一条命令跑完全流程：日期只解析一次，自动挑补算板块，失败即停
└── selftest.py    # 六项自测，含与 v1.6 已知答案的逐位对照
```

九个关键设计（1–4 是取数与组装，5–7 是让数字站得住的一致性约束，8 是数据源降级，9 是不让日期靠人记）：

**1. 批量报价替代逐只 K 线。** P2 广度只要两个量：当日上涨占比、当日是否创 20 日新高。前者批量报价直接给（60 只一次），后者需要 21 天历史。所以首次建库逐只拉 K 线存进 sqlite（一次性），之后每天只补当日报价——K 线请求从每日 232 次降为 0 次。实测 8 个板块的 P2 与 v1.6 报告逐位一致（白酒 94.7%/42.1%、银行 69.0%/42.9%、铁路公路 24.2%/3.0% …）。

涨跌判定必须用「现价 vs 昨收」的原始价格，不能用报价里的 `chg_pct`：百分比只保留两位小数，±0.005% 以内的波动会被截断成 `0.00%`，把微涨误判成平。吉比特 603444 当日 +0.003%，用 `chg_pct` 会让游戏Ⅱ 的上涨占比从 4.2% 掉到 0.0%。

**2. 契约前置校验。** 每个源先拉 1 条样本断言「字段存在 / 目标日期命中 / 数值可解析」，不通过就在 1 秒内失败并给诊断。区分 `required` 与可降级：日 K 接口不可用时，只要本地库有数据就继续跑并标注 `[DEGR]`。

**3. 熔断。** 连接层被 RST（HTTP 000）时零重试——重试对封禁无效，只会空转。连续 3 次即熔断 300 秒，后续请求快速失败。实测 6 次尝试从旧实现的约 108 秒压到 3.6 秒。

**4. 报告模板化。** `weights`/`stage_rules`/`glossary`/`method_summary` 每期完全一致，抽到 `templates/static.json`，生成端只写变化部分，体积从 28.5KB 降到 24.2KB（−15.3%）。组装时自动跑一致性自检：权重合计 100、`score = Σ贡献 − 惩罚`、六因子齐全、由 metrics 重算的闸门数与声明值一致。

```bash
python -m pipeline.daily                      # 全自动：自动判日期 → 一路跑到成品页（97 秒）
python -m pipeline.daily --until score        # 只取数算分，留出写叙事的时间
python -m pipeline.daily --dry-run            # 只打印将执行的命令，不发请求
python -m pipeline.day                        # 单独看「今天该用哪个交易日」
python -m pipeline.selftest --full   # 八项自测，含 P2 逐位对照 + 缺口/复权回归（离线）
python -m pipeline.repair_kline --as-of 2026-10-30 --check   # K 线库体检，不发请求
python -m pipeline.repair_kline --as-of 2026-10-30 --rebuild # 清空后全量重建（换复权口径时）
python -m pipeline.run --as-of 2026-10-30
# 取数节奏的默认值来自 templates/fetch_policy.json（并发 4 / 4 rps / 铺开 ≥40s）
python -m pipeline.run --as-of 2026-10-30 --workers 4 --rps 4 --min-span 40
python -m pipeline.run --as-of 2026-10-30 --cache-ttl 1800   # 崩了重跑：同 URL 半小时内零请求
python -m pipeline.run --as-of 2026-10-30 --no-journal        # 不落逐请求 journal
```

**5. 增量库的缺口契约。** P1/P3 每次全量重拉面板、涨停池带日期可回溯，对「几天不跑」免疫；只有 `kline.sqlite` 是 append-only 的，需要三条硬规则兜住：

- **缺口按日历判，不按根数判。** 旧判据 `count < 25` 永远看不出缺口——count 只增不减，跳过的日子既不入库也不触发重拉，20 日窗口被悄悄向后拉伸。实测 5 日缺口让汽车零部件新高从 0.73% 涨到 7.27%（10 倍）、银行Ⅱ 从 42.86% 到 57.14%，而白酒Ⅱ 反而从 42.11% 降到 31.58%——方向都不一致，事后无法修正。现在拿 `panel.by_date` 当交易日历逐日比对，缺一天就整只重拉（`INSERT OR REPLACE` 天然补洞）。
- **K 线日期取报价自带的交易日，不取 `as_of`。** 非交易日跑分析会把周五收盘写成周日的假 K 线，那天 `prev_high` 恰好等于同一价格，新高占比直接归零（实测白酒Ⅱ 42.11%→0.00%，P2 由「过」翻成「不过」）。盘中跑（时间戳 < 15:00）写入后打 `provisional` 标记，下次运行整只重拉修正。
- **判不了就不判。** `breadth()` 拿到日历后逐日比对，某天被过半成分股同时缺（缓存漏了一段）就置 `degraded`，`run.py` 对该板块 fail-closed。单只股票缺几天不算——停牌股天然缺日（新华传媒停 3 天、路畅科技停 10 天），次新股天然不到 45 根，两者都不该把整块 P2 判死。

涨跌占比这一半不受缺口影响：`prev_close` 来自腾讯报价，永远是真实前一交易日收盘，与本地库无关。

**6. 复权口径统一。** 旧库混了三种价：腾讯 `qfq` 前复权、新浪不复权、每日报价的原始收盘。每次除权 `qfq` 锚点整体平移一次（实测工行 200 日窗口内 `qfq/raw` 从 0.9592 漂到 0.9596），拼接处出现假跳空，20 日高点被系统性高估。

- **库内只存连续复权序列 `c`**（建库取 `qfqday`，之后由报价滚动延续），`r` 存最近一次写入的原始收盘，仅供核对。P2 只关心同一只股票内部的相对关系，跨股不可比也无所谓。
- **换算只有一行**：`c(t) = P × c0 / PC`（`P` 现价、`c0` 库内最后一根、`PC` 报价昨收）。除权日交易所给的 `PC` 已经调整过，所以这一个式子同时处理平推与除权，**不需要复权因子表，也不需要除权日历**。实测 1 拆 2 场景写回值误差 0，序列比值与真实收益率逐位一致。
- **重拉必须整只替换**（`Store.replace_many`，先删后写）。`qfq` 与新浪不复权只差一个等比因子，不清理就覆盖会让同一只股票同时存在两种基准。
- 换算后日涨跌幅超过交易所上限（31%）直接拒写，宁可空一天等重拉，也不把错价写进窗口。

**7. 取数节奏：并发 4 / ≤4 rps / 整轮铺开 ≥40 秒。** 前三版都在优化「更快」，这一版反过来优化「更稳」——因为 128 个板块 + 485 只成分股的全量真取是每天都要跑的，只要有一轮触发风控，代价远大于省下的十几秒。

四层闸门缺一不可（`pipeline/http.py`，参数在 `templates/fetch_policy.json`）：

| 层 | 作用 | 为什么不能省 |
|---|---|---|
| 全局槽位 | 所有 host 共用一个 `next_slot`，按固定间隔排期 | 只有 host 限速时，两个 host 同时开工的瞬时速率是两者之和 |
| host 槽位 | 单 host 更严的上限（东财 3.5 / 腾讯日 K 2.5 / push2his 2.0 rps） | 腾讯日 K 超 3 rps 直接返 501 风控页 |
| 速率预算 `plan(total)` | gap = `max(1/max_rps, (deadline−now)/(剩余−1))`，**最后一槽正好落在 deadline** | 让「156 次摊到 40 秒以上」成为可断言的性质，不靠调参碰运气 |
| AIMD 自适应 | 遇 429/503/5xx/WAF 把**该 host** rps 砍半，每 20 次成功回升 15% | 只惩罚出问题的源；腾讯被拦不该拖慢东财 |

配套三件事：

- **`Retry-After` 优先于指数退避**——服务端说等多久就等多久。
- **逐请求 journal**（`cache/http-<as_of>.jsonl`）：偏移时刻、host、HTTP 码、耗时、字节。`run.json` 的 `fetch_audit` 由它聚合出实测跨度 / 实测 rps / 峰值并发 / 逐 host 分布，`deep_audit` 再断言「跨度 ≥40s、rps ≤4、峰值并发 ≤4、任意 10 秒窗口无突发、per_host 计数与 journal 一致」。**「没被限流」从自述变成了可复核的断言。**
- **同一份数据不取两次**：`run.py` 把报价快照落盘，`score.py` 判龙头时直接读（省 9 次请求）；面板 pkl 也由 `run.py` 当场落盘，下游按指纹复用（省 128 次）。

实测（2026-10-30 全量真取）：**156 次请求 / 45.8 秒 / 3.40 rps / 峰值并发 3 / 0 失败 0 封禁 0 重试**，最密 10 秒窗口 37 次（上限 46）。同一份数据换回 12 并发 + 10 rps 是 21 秒——快的部分被风控风险吃掉了。

**8. 全市场广度：push2 被 RST 时改走新浪全 A 快照。** `market_regime.breadth.up_ratio` 需要全市场口径，东财 `push2` / `push2delay` / `82.push2` 三个域名在部分网络下**连接层**就被 RST（HTTP 000，不是 4xx/5xx），重试无效——这正是 `http.py` 对 000 零重试的原因。备用通道是新浪 `Market_Center.getHQNodeData`（`node=hs_a`），单页上限 100 条，分 56 页拉全量，约 30 秒。

选它而不是现成的「涨跌家数」计数接口，理由是**可审计**：每只个股的收盘价、涨跌幅、成交额都在本地，涨跌家数、涨跌比、涨跌分布、分市场占比全部由同一份快照现算，读者可以自己数一遍。顺带解决的还有份额分母——板块面板反推的成交额合计 17951.88 亿，与快照实测 17949.0 亿相差 +0.016%，`turnover_share` 的分母因此不再需要标「代理」。

口径必须写死，否则同一份报告会出现两套数：有效样本 = 有成交（`volume>0` 且 `price>0`），停牌股不计入分子分母；`up/down/flat` 按收盘涨跌幅严格 `>0 / <0 / ==0` 划分。2026-11-02 实测：全 5576 只、有效 5570 只（停牌 6）、上涨 4680 / 下跌 818 / 平盘 72 → `up_ratio = 4680 ÷ 5570 = 0.8402`、涨跌比 5.72；含北交所 0.8402 与剔除北交所后沪深 0.8399 只差 0.03pct，结论不受口径影响。

单一快照源要能自证：`--verify` 抽 17 只（含 1 只北交所）与腾讯 `qt.gtimg.cn` 逐只比对，一致 17 只，价差 0.000%、涨跌幅差 ≤0.005pct、成交额差 ≤0.02%（腾讯成交额字段单位是**万元**，除以 1e4 才是亿元——踩过一次，全部 17 只被误判为「偏差超阈值」）。

仍未取的是 `new_high` / `new_low`：要 5000+ 只个股各 21 根 K 线，单份报告 60 次请求的预算装不下，故写 `null` 并列入 `missing`；页面显示「新高 —」，不用 0 填充。

```bash
python -m pipeline.breadth --as-of 2026-11-02 --verify   # 拉全 A 快照 + 统计 + 交叉校验
python -m pipeline.breadth --as-of 2026-11-02 --cache --verify   # 复用已落盘快照，零请求
```

**9. 日期不许手填：`--as-of` 缺省即自动。** 这一版之前，9 个模块各自硬编码 default（10-30 与 11-02 混着），`--as-of 2026-11-03` 这种写法第二天就错；更危险的是「主参数改对了、`build_v16` 仍指旧日期」——它会拿昨天的板块名套今天的数字，生成一份不报错但结论全错的报告。

推导不靠节假日表，靠**行情自己回答哪天有过交易**：取上证指数最近 80 根日 K，`days[-1] == 今天` 且已过 15:05 就是今天；`days[-1] == 今天` 但还没收盘就取 `days[-2]`（当天 K 线不完整）；`days[-1] < 今天` 说明是周末/节假日，直接用它。国庆、春节、临时休市都不用维护日历。实测：周日 20:00 → 10-30；国庆假期内 → 09-30；10-08 盘中 10:00 → 09-30，10-08 收盘后 → 10-08。

三个必须踩过的坑：

- **显式日期不许联网校验。** 一开始 `resolve("2026-11-02")` 会顺手验「这天是不是交易日」，而 `daily` 要把同一日期传给 9 个子进程——等于多打 9 次日 K 接口，实测把腾讯打到 501，最后一步组装直接崩溃。现在显式日期只校验格式。
- **自动推导必须落磁盘缓存**（`cache/trading-days.json`，TTL 10 分钟），否则同样是 9 倍请求。
- **日 K 不可用时要降级**，不能抛异常中断整条流水线：退到 `kline.sqlite` 里出现过的日期（那本来就是真实交易日）。三层依次是内存 → 磁盘 → 行情接口 → 本地库。

`daily.py` 另外守住两件容易静默出错的事：上榜板块若在 `CONTENT`（主线文案）或 `narrative.json`（叙事分）里找不到，**拒绝组装并退出码 2**，而不是默默用 0 分或旧文案；`extra` 改为增量写（`--fresh` 可整体重算），否则「只补 4 个新板块」会把上一批 11 个板块的 P2 冲掉，`rotation.emerging` 跟着变样。

## JSON 契约

- 顶层 12 个键**全部必填**：`schema_version / meta / window / data_quality / market_regime / verdict / mainlines / rotation / risks / scenarios / playbook / appendix`。
- 百分比一律用**小数**（5.21% → `0.0521`）；金额单位「亿元」且字段名带 `_yi`；数字必须是 JSON 数值类型，不能加引号。
- 数值缺失用 `null`（可选字段允许 `null`，必填字段必须有值）；数组为空用 `[]`。
- `score = Σ contribution − penalty`，`score_breakdown` 可复现该值（±0.5）。`contribution = normalized × weight / 100`。
- `score_breakdown[].raw`（`rs` 那一行）与 `metrics.rs_20` **必须是同一个数**。`rs` 是**净值比** `(1+板块收益)/(1+基准收益)`（1.0 = 与大盘同步），不是超额收益百分点；基准固定为中证全指 `000985.CSI`，取不到时才用沪指代理并注明。
- 拥挤惩罚只有三档：`R1 −12`（份额分位 >0.95 且 连板 ≥5）、`R2 −6`（份额分位 >0.90 且 拥挤度 >0.90）、`R3 −8`（60 日涨幅 >60% 且 5 日资金净流出）；**多项命中取最大值**，`penalty_reason` 必须写明编号与实算。
- `stage` 有**裁决顺序**：`fade → divergence → acceleration → expansion → ignition`，取第一个满足 ≥2 项判据的阶段（越靠后优先级越高，因为它描述更晚发生的状态）。判据所需字段为 `null` 时记「无法判定」，可判定项不足 2 项则该板块**不得进入 `mainlines`**（schema 的 `stage` 不允许 null），改列 `rotation.emerging`，不许猜一个填上。
- 页面导入是**宽松归一化**：缺结构补空数组/空对象，**但缺数值不补 0**——页面显示「—」或「未判定」，不会把没取到的数据伪装成结论。数字写成字符串、比率写成百分数会被自动折算并在诊断里逐条列出；`chg_*` 落在 1～3 区间的折算会额外标「可能是真实涨幅，请复核」。

### 为什么 `metrics` 有 23 个字段

因为**每条硬规则都要能当场算出来**。v1.5 补了三个字段，正是为了让五个阶段判定全部可复算，而不是靠模型「看盘感」：

| 新增字段 | 口径 | 谁来验算 |
|---|---|---|
| `turnover_share_chg_20` | 份额相对 **20 个交易日**前的变化（0.012 = +1.2pct） | `fade` 判据「份额 Δ20 < −0.5pct」 |
| `max_streak_prev` | **5 个交易日前**的连板高度 | `divergence` 判据「连板回落 ≥2 级」（`max_streak_prev − max_streak`） |
| `leader_chg_5d` | 板块内**龙头个股**的 5 日涨跌幅（不是板块的 `chg_5d`） | `fade` 判据「龙头 5 日跌幅 >8%」 |

补齐前，`fade` 的三条判据全部没有对应字段、`ignition` 与 `divergence` 各缺一条——**阶段判定事实上不可复算**，而 `stage` 是全篇权重最高的字段。

## 输出体积：唯一的硬约束

实测体积：字段全空约 **6K 字符**，3 条主线约 **20K**，5 条主线约 **32K**，硬上限 **40K**。而单条回复的输出上限常常在 6–8K tokens 量级。装不下时模型只有三条路：省略（写 `...`）、截断（写到一半停）、或者放弃格式改成一段说明文字——三条路都等于「拿不到可解析的 JSON」。

所以提示词把体积当成第一约束处理，而不是靠模型自觉：

- **排版按骨架**：一个顶层键一行，对象内联。实测同样的内容，逐字段缩进会从 7.8K 膨胀到 10.7K 字符，这是截断最常见的诱因（§10-D 第 11 条）。
- **压缩有顺序**：接近上限时按 `detail` → `note` → `narrative` → 主线数量依次压，**绝不删字段、绝不中途停止**（第 12–14 条）。
- **失败有台词**：被截断后不要回「继续」（续写出来的是接不上的碎片），改用 §13 给出的重试指令，让模型「mainlines 只保留闸门合格条目（最多 3 条）、detail 压到 40 字」整段重发。

配 API / Agent 用时另有两点实操：先关掉「深度思考」（思考过程吃掉一半输出预算）；复制时点代码块的复制图标，长代码块有内部滚动条，鼠标框选只会拿到可见部分。

## 为什么模型给的 JSON 经常「复制不了」

这不是模型不听话，是两个具体的机制问题，v1.1 从两边都堵住了。

**原因一：提示词没说清结构，模型只能猜。** 早期版本只在文首写了一句「配合 schema 输出」，但模型看不到 `schema/*.json` 文件，字段名全靠自由发挥——`score_breakdown` 写成 `scoreBreakdown`、`pulse_check` 写成 `persistence_check`、甚至把 6 个因子压成一个总分。结构一旦跑偏，复制出来的就是「看起来像 JSON」的文本。

v1.1 的解法：把**完整骨架（12 个顶层块、逐层到 `metrics` 的 23 个字段）直接写进提示词 §9**，并注明「键名照抄，不得增删改名」，附枚举取值表。已用脚本校验：骨架与 `samples/sample-report.json` 的键集合完全一致，且骨架本身是合法 JSON（不是伪代码）。

**原因二：输出层的三类瑕疵。** 模型常干三件事，任何一件都会让 `JSON.parse` 直接失败：

| 瑕疵 | 典型形态 | 页面处理 |
|---|---|---|
| 代码围栏 | ` ```json … ``` ` | 自动剥离，含前后说明文字 |
| 尾部语法 | 尾逗号、`// 注释`、中文引号当分隔符、Python 字面量 `None/True` | 逐项清洗后重试 |
| 截断 | 输出到一半被 max_tokens 切断 | 在最后一个完整元素处截断并补齐括号 |

同时提示词 §10 把规则写成了硬约束：只输出 JSON、不加围栏、**禁止 `...` / 「其余同上」类占位符**、禁止注释与尾逗号、并给出长度预算（`detail ≤ 120 字`）与压缩顺序（先压文字，绝不删字段、绝不中途停止）。§12 处理「一次装不下」的情况：先输出完整 JSON，再另起一条消息解读，禁止把一条 JSON 拆成两半。

**导入时的诊断**：抽屉里会显示一行结果——成功的写「✓ 解析成功 · N 条主线」并列出做了哪些修复，失败的写清是「没找到 JSON」还是「解析成功但没有 mainlines」，不会再只丢一句 `Unexpected token`。另有「仅校验」按钮，先看结果再决定是否覆盖当前页面。

若模型仍然不配合，把提示词 §13 的重试指令原样回给它即可。

## 契约体检：页面不信报告的自述

一份报告最危险的不是格式错误，而是**每个字段都合法、结论却算不出来**——比如 `rules_passed: 3` 而 `metrics` 实际只过 1 条，或者 `stage` 写「加速期」而 `crowding_pct` 只有 0.62。

v1.5 在页面里加了一层 `auditReport()`：把提示词里那些**机械可判**的硬规则全部重算一遍，和报告声称的结论逐项比对。算不出来的（字段为 `null`）标「无法验算」，不拿默认值冒充。

| 复算什么 | 用哪些字段 | 对不上时 |
|---|---|---|
| 反脉冲条数 | `days_top10_20`、`consecutive_top10`、`breadth_up_ratio`、`new_high_ratio`、`turnover_share_chg_5`、`turnover_share_pct_250` | `err` |
| `passed` 与实算是否一致 | 同上 | `err` |
| 是否该进榜（含 `fade` 存量豁免判定） | 实算条数 + `stage` + `stage_confidence` + `rotation.outflow` | `err` / `info` |
| 惩罚 R1/R2/R3 | `turnover_share_pct_250`、`max_streak`、`crowding_pct`、`chg_60d`、`net_inflow_5_yi` | `err` |
| 阶段判据 | 五阶段各自的 3–4 条阈值，按裁决顺序取第一个 ≥2 项 | `warn` |
| 六因子算术 | `normalized × weight / 100 = contribution`，权重合计 100，六项齐全 | `warn` |
| `rs` 口径 | `score_breakdown[rs].raw === metrics.rs_20` | `warn` |
| 总分复算 | `Σ contribution − penalty` 与 `score` 相差 ≤0.5 | `err` |
| 证据链 | `drivers` 至少 2 条 | `warn` |
| 全局 | 情景恰好 3 个、概率和 = 1、`mainline_count` 对得上、`rank` 从 1 连续、按分数降序 | `warn` |

三处呈现，同一个数据源：

1. **结论区顶部一条横幅**：`✓ 契约体检通过` 或 `⚠ 契约体检：N 处待核`，点进去直接跳到口径章节的完整明细。
2. **排行表每行的 `⚠N` 角标**：鼠标停留即列出该条主线的全部问题，不用滚动。
3. **单条主线拆解区**：把该条的问题逐条摊开，`不一致` / `待核` / `说明` 三级分别对应 `err` / `warn` / `info`。

另外**归一化动过的手脚也会留痕**：加载旧报告时没人会去翻导入抽屉，所以只要 `normalize()` 改过字段（字符串转数值、百分数折小数、非法枚举置空），体检里会多一条「有 N 处字段在渲染前被自动修正，页面显示的是修正后的值，不是报告原文」。

拿真实的旧报告 `aml-20261030.json` 试过：`err=0 warn=1`，准确指出「#2 大消费 按判据应为发酵期而非启动期」——这类问题用肉眼翻 JSON 是看不出来的。

## 页面能力

- 六因子打分 + 拥挤惩罚的主线排行，表头可排序，点击行切换详情
- **契约体检**：把 P1/P2/P3 闸门、R1/R2/R3 惩罚、五阶段判据、六因子算术全部按 `metrics` 重算一遍，与报告自述逐项比对（详见上一节）
- 导航随滚动联动：scrollspy 按「section 顶部越过导航下方 96px」判定当前章节，点击页签平滑跳转并锁住高亮 700ms，避免途经章节闪跳；当前页签用一条按文字宽度量取的滑动下划线标识（淡入 + 位移过渡），窄于 960px 时整组页签隐藏，绝不折行
- 单条主线拆解：分数环、阶段轨道、因子条、证据链、龙头梯队、证伪条件、观察清单、提前失效条件（`horizon.review_trigger`）
- **时效性横幅**：基准交易日距今 >7 天标「数据陈旧」，`horizon.valid_until` 已过标「结论已过期」并写明距今多少天——旧报告不该看起来和新报告一样可信
- **三态显示**：有值 / 无值（`—`）/ 不可验（`未判定`、`未检验`、`龙头未判定`）。缺数据时不会掉成 0 分、0% 或默认阶段
- 资金轮动、风险清单、情景概率、操作框架、数据口径与缺失说明（含量化窗口内已剔除的区间、提示词版本、操作者）
- 导入 / 导出 JSON、复制提示词 / Schema / 空白模板、打印（自带 print 样式）
- 导入容错：自动处理代码围栏、前后说明文字、尾逗号、注释、中文引号、Python 字面量、中段截断，并在抽屉里报告做了哪些修复
- 多段合并：模型分两次回复时，把几段 JSON 一起粘进来自动按主线合并去重（其余字段取第一份有值的）
- 导入结果写入 localStorage，下次打开自动恢复；抽屉里可「恢复示例数据」
- 全离线：Vue 与 Inter 字体均为本地文件，断网可用，不产生外部请求

测试分两层，缺一层就会出现「页面没崩、结论是错的」。

**格式层（36 条）**——曾经踩过的坑：字符串数字（`"87.6"`）导致 `toFixed` 抛错白屏、比率缩放漂移（`72` 被当成 `7200%`）、缺数据被渲染成默认阶段或 0 分、截断的 5 条盖掉完整的 3 条、内置样例在归一化过程中被改动（应为 0 处）。

**语义层（18 条）**——检验报告本身讲不讲得通：

| 断言 | 为什么要它 |
|---|---|
| 内置样例通过契约体检（`err=0`） | 样例是模型的模仿对象。样例违反自己的闸门，等于教模型怎么把不合格主线留在榜上——这正是 v1.4 的真实 bug |
| 样例五条主线的阶段、惩罚、反脉冲条数、`rs.raw` 全部可复算 | 证明「判据都可算」不是口号 |
| 谎报反脉冲 / 惩罚与 R1R2R3 不符 / 未过闸门 → 三类脏数据必须被抓出 | 体检本身也要被测试，否则它只是个装饰 |
| `fade` 存量豁免不被误判为错 | 豁免是唯一允许「不过闸门还留在榜上」的路径，误杀会让它失效 |
| 情景概率和 ≠1、`rs.raw ≠ rs_20` → 标出 | 全局一致性与口径统一 |
| 阶段冲突时按裁决顺序取更晚的那个 | 同时命中 `acceleration` 与 `divergence` 时不能挑「最像的」 |
| 非法枚举 → `null`、中文枚举 → 对应值、`stance_label` 缺失按枚举回填 | 渲染层不该把 `liquidity` 这种旧值原样露出来 |
| `chg` 落在 1～3 区间折算时标注「请复核」 | 1.05 可能是 105%，也可能是 1.05%，页面不能默默替你决定 |
| 体检可跑在 Vue 响应式代理上 | 防止 `Object.defineProperty` 的不可配置属性让整页白屏（踩过一次） |

契约本身可以直接用 JSON Schema 校验：

```bash
python -c "import json,jsonschema as j; \
s=json.load(open('schema/ashare-mainline.schema.json',encoding='utf-8')); \
d=json.load(open('samples/sample-report.json',encoding='utf-8')); \
j.Draft7Validator(s).validate(d); print('schema ok')"
```
